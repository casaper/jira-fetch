# Contributing

Thanks for looking. This is a small project with one maintainer, so the shortest path is usually an
issue describing what you hit before a pull request that fixes it.

> **This project was written entirely by AI**, in a series of prompted Claude Code sessions. That is
> not an excuse for a sloppy patch — the conventions below are enforced by tooling and by
> [CLAUDE.md](CLAUDE.md), which is the file those sessions read. If you change something the file
> describes, change the file too.

## Getting set up

Deno 2.x and nothing else. There is no `node_modules`, no lockfile to install and no build step for
development.

```sh
git clone https://github.com/casaper/jira-fetch.git
cd jira-fetch
deno task hooks   # once per clone: enables the Conventional Commits hook
deno task test
```

`deno task hooks` sets `core.hooksPath`, which is local git config and therefore cannot be
committed. Until you run it, nothing checks your commit messages and CI will be the one to tell you.

## The tasks

```sh
deno task check      # typecheck + lint + fmt --check + generated-file freshness
deno check test/     # `check` covers src/ and scripts/ only — tests need this separately
deno task lint
deno task fmt
deno task test       # or: deno test -A
deno test -A --filter "excludes anonymous reporter"   # a single test by name
deno test -A src/adf/to_markdown_test.ts              # a single file

deno task dev DN-1243 --out tmp   # run the CLI from source
deno task mcp                     # run the MCP server from source, on stdio
deno task verify:filters          # filter scenarios against the REAL Jira site (needs credentials)

deno task schema     # regenerate schema/jira-fetch.schema.json
deno task types      # regenerate src/jira/schema_types.ts from the vendored specs
deno task build      # host binary into dist/
deno task build:all  # all six release targets
deno task npm:pack   # stage the seven npm packages into dist/npm, without publishing
```

> **`deno task dev` is live-fire in this repository.** Configuration is derived from the git
> repository you are in, so a run inside this checkout resolves _your own_ `jira-fetch` config file
> and talks to your real Jira site. There is no offline mode; use the test suite for that.

## The test suite is sealed

`deno task test` needs **no credentials and no network**. `test/e2e_test.ts` drives the entire CLI
against a fake Jira on localhost (`test/fake_jira.ts`), and `test/mcp_test.ts` drives the MCP server
against the same one. That is what covers the wiring in `src/main.ts`.

Sealing it is deliberate and it is fragile in one specific way. `run(argv, deps)` takes
`projectRoot` and `configDir`, and when both are given they are used verbatim — no walk for `.git`,
no `$HOME`. **Any new entry point that calls `run` from a test must pass both**, or the run works
out which repository it is in and reads your real configuration, token included. Nothing asserts the
token, so a leak would not turn the suite red; it would just quietly stop being hermetic.

`deno task verify:filters` is the complement and is deliberately **outside** that suite: it runs a
table of allow/deny/both scenarios against your real Jira site, works out what each one should keep
from the tickets' actual fields with an oracle that imports nothing from `src/filter/`, and compares.
Agreement between the two is the evidence. It skips with a message and exit 0 when no credentials
are configured. Documents land in `tmp/filters/` and are left there, so the run doubles as a way to
see what the tool produces for real tickets.

## CI

[`.github/workflows/ci.yml`](.github/workflows/ci.yml) runs on every push to `main` and every pull
request:

- **check** (ubuntu) — `deno task check`, then `deno check test/` as its own step, then the commit
  messages on pull requests only.
- **test** (ubuntu, macOS, Windows) — the full suite, `fail-fast: false` so one red platform does
  not hide the others.

`deno task verify:filters` is **not** in CI and must not be added. It exits 0 when no credentials
are configured, so it would pass every time having verified nothing.

## Code style

`deno lint` and `deno fmt` are the whole toolchain. `deno.json` and `.editorconfig` settle the rest:
2-space indent, LF, 100 columns, semicolons, **single quotes**, and `proseWrap: preserve` so
hand-wrapped Markdown is left alone.

Three conventions no rule can express — follow them in new code anyway:

- **arrow functions** over `function` declarations
- **`type`** over `interface`
- **string-literal unions** over `enum`

Most existing source predates them and still uses `function` and `interface`. Convert it when you
are already editing it, not as a sweep.

## Generated files, which are never hand-edited

| File                                | Regenerated by           | Checked by          |
| ----------------------------------- | ------------------------ | ------------------- |
| `schema/jira-fetch.schema.json`     | `deno task schema`       | `deno task check`   |
| `src/jira/schema_types.ts`          | `deno task types`        | `deno task check`   |
| `CHANGELOG.md`                      | `deno task changelog`    | `deno task release` |
| the npm manifests and the Node shim | `scripts/npm_package.ts` | `deno task test`    |

`src/jira/schema_types.ts` derives from Atlassian's own published Jira and ADF schemas, vendored and
pinned under `spec/` (both Apache-2.0 — see [spec/NOTICE](spec/NOTICE)). `deno task vendor:spec` is
the only task in the repository that touches the network, and it is run by hand.

Configuration has one source of truth as well: the Zod schemas in `src/config/schema.ts`. Adding a
config option means editing those and re-running `deno task schema` — the TypeScript types, the JSON
Schema and the runtime validation all derive from them.

## Commit messages

[Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/), enforced by
`.githooks/commit-msg` and again in CI:

```
type(scope)!: subject
```

Types and scopes are declared in [`scripts/commit_lint.ts`](scripts/commit_lint.ts); the header is
capped at 72 characters, imperative, lower-case, no trailing period, and bodies wrap at 100. The
convention governs the **subject line only** — this project's commit bodies explain _why_, at
length, and [CHANGELOG.md](CHANGELOG.md) is generated from the subjects.

`deno task commitlint --from <rev>` lints commits that already exist, which is how a rebase gets
verified before it is pushed.

## Releases

Maintainer-only, and from a developer's machine rather than CI:

```sh
deno task release patch              # bump, changelog, commit, tag, push, build, publish
deno task release patch --no-publish # stop at the tag
deno task publish                    # just the publish half, if a cross-compile failed
```

Publishing is a task of its own because cross-compiling six targets is the step most likely to fail,
and the fix has to be `deno task publish` again rather than a bumped, tagged version with nothing
behind it. It attaches the six binaries to a GitHub release and then publishes seven npm packages.
**The npm half cannot be undone** — a published version is unpublishable after 72 hours and can
never be republished, so a mistake in `x.y.z` is permanent and the fix is `x.y.z+1`.

[CLAUDE.md](CLAUDE.md) documents the traps in that path in detail.
